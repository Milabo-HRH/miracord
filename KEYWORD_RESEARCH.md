Historical research notes. The current optional cascade uses configurable
Paraformer wake/stop detection; see PIPECAT.md. Download experimental sherpa
bundles separately from the linked model documentation; they are not included
in this change. Sections below describe dated experiments, not current defaults.

## Current deployment: Chinese-only controls

Updated late 2026-09-04 after gameplay reports. The user requested removal of
`over`. The deployed model is now WenetSpeech 3.3M, with `豆包`, `结束`, and `闭嘴`.
The Chinese `keywords_control.txt` uses normal and neutral-tone `豆` variants
(score 3.0, threshold 0.05), with shut-up also at (3.0, 0.05) and end at (1.0, 0.25).
Only one detector runs per user. `结束` closes input while allowing the answer
to continue; `闭嘴` additionally cancels the answer.

The bilingual deployment missed all four wake words in one synthetic Mandarin
sample. The final Chinese configuration detected four of four and produced no
keyword hits on nine supplied negative clips totaling about one minute. Results
are in ignored `logs/evals/wake-chinese-controls.json`. The positive sample was
generated by Gemini without playback or player recording. This is a narrow
regression check, not measured gameplay accuracy or stop-word recall.

## Initial research (superseded deployment)

The following initial research was reviewed 2026-09-04 without microphone,
Discord session, or paid API use; the later live synthetic check is described above.

### Initial model choice

The new default is the already downloaded **sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20**. It supports Chinese and English, so one local detector can recognize `豆包`, `闭嘴`, `结束`, and `over`. The previous default WenetSpeech 3.3M release supports Chinese only. This corrects the handoff's description of that older release as bilingual. Official docs offer chunk-8 (160 ms) and chunk-16 (320 ms); this integration retains chunk-16 and pairs int8 encoder/joiner with the available fp32 decoder. These are model chunk latencies, not measured end-to-end response times. [Official sherpa model documentation](https://k2-fsa.github.io/sherpa/onnx/kws/pretrained_models/index.html)

The decision improves language coverage, **not a claim of measured accuracy improvement**. No representative gaming speech corpus was available. The prior custom keyword file forces score 10 and threshold 0.001 for several pronunciation variants; the new control file omits those overrides and uses configured global values. Threshold changes trade missed detections against false activations and need evaluation.

[Porcupine](https://github.com/Picovoice/porcupine) also supports Mandarin and custom wake phrases. Its [Python integration](https://github.com/Picovoice/porcupine/blob/master/binding/python/README.md) requires an AccessKey and language-specific models. It remains a future A/B candidate rather than adding an account dependency in this change. [openWakeWord's official README](https://github.com/dscripka/openWakeWord#language-support) currently describes English support only, so the existing Alexa fallback is not a Chinese upgrade.

## Local gate behavior

Each allowed Discord user has an independent streaming detector and input gate. Start and stop predictions preserve their actual keyword labels; the old wrapper incorrectly mapped any nonempty detection to the configured wake phrase. For the default model, keywords are tokenized in `keywords_control.txt`, including `OW1 V ER0` for `over`, checked against the bundled English pronunciation lexicon.

A stop detection closes only that speaker's input synchronously before the detection frame is sent. Pending local audio is discarded; queued audio carries a generation token so it cannot resume after a stop/wake cycle. Audio remains local until the same speaker says the start phrase again. Stop detection also receives trailing synthetic silence when Discord suppresses RTP, and remains enabled while the speaker is active. Guild integration distinguishes input closure from output cancellation. `over` / `结束` mute only that user's input, finalize audio already delivered to the provider, and let the agent continue its answer. `闭嘴` additionally cancels that user's current answer and stale tool work. Another user's turn is unaffected. Structured `input.gate.closed` / `input.gate.open` events contain a pseudonymous speaker identifier and the configured keyword.

Streaming recognition cannot retract PCM already delivered before a keyword is recognized. Input muting stops further upload, and `闭嘴` additionally requests cancellation/suppression. `over` / `结束` deliberately preserve the answer to previously delivered input. None of these operations provides whole-utterance redaction or guarantees that the stop phrase's initial audio never reached the provider. Achieving that would require buffering whole utterances and paying additional latency. Ordinary speech containing a configured stop phrase can close the gate; this is keyword spotting, not intent classification.

## Configuration and fallback

- `WAKE_WORD_ENGINE=sherpa_onnx` enables bilingual control. The existing openWakeWord fallback does not contain Chinese/English stop models.
- `SHERPA_WAKE_WORD_MODEL_DIR` overrides the asset directory; `SHERPA_WAKE_WORD_KEYWORDS_PATH` overrides the tokenized control file.
- `STOP_WORD_ENABLED=true` and `STOP_WORD_PHRASES=闭嘴,结束,over` select stop labels. Adding labels also requires corresponding tokenized entries; changing the environment list does not train a model.
- The legacy Chinese model directory contains its own `keywords_control.txt` with Chinese commands only. Set its directory and `STOP_WORD_PHRASES=闭嘴,结束` to revert.
- Changing `WAKE_WORD_PHRASE` requires a matching tokenized keyword file. Existing repeated-phrase aliases remain supported by the adapter.

## Evidence and follow-up evaluation

Mocked regression tests cover actual stop result labels, repeated-wake expiry/reset, per-user stop/wake isolation, detection-frame suppression, stale queued audio across reopening, stop finalization after RTP gaps, session persistence, and disabling stop detection. A local ONNX load/silence smoke check confirmed all default assets and keyword tokens load and silence returns no detection. These checks do not establish recognition accuracy.

For an accuracy decision, use a separately consented, locally stored corpus with positive examples of each command at normal/quiet/fast speaking rates and gaming-noise negatives (including near-homophones and ordinary uses of “结束” / “over”). Freeze speaker-independent train/tune/test splits, model hashes, keyword file, score and threshold. Report misses per positive command, false activations per negative-audio hour, and median/p95 detection delay, separately by speaker and noise level. Compare both sherpa releases on the same Chinese subset; evaluate English separately. Do not commit private audio or transcripts. The prompt/tool replay suite tests routing behavior; it does not substitute for an acoustic benchmark.
